# Changes from the Original CRM Repository

This document records every modification made to produce the No-Docker version. The original repository is assumed to be the version at `F:\crm` (the source monorepo with Docker support). All changes are dated **2026-08-24** unless otherwise noted.
---

## 1. Removed Docker Dependency

### What changed

**Removed files:**

- `docker-compose.yml` — the Docker Compose definition that started a PostgreSQL 17 container. Its content was:

  ```yaml
  services:
    postgres:
      image: postgres:17-alpine
      container_name: crm-postgres
      restart: unless-stopped
      environment:
        POSTGRES_USER: postgres
        POSTGRES_PASSWORD: postgres
        POSTGRES_DB: crm
      ports:
        - "5432:5432"
      volumes:
        - crm-postgres:/var/lib/postgresql/data
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U postgres -d crm"]
        interval: 3s
        timeout: 5s
        retries: 20
    volumes:
      crm-postgres:
  ```

- From `eve-0.31.2/` — the local eve distribution used as a reference. This directory is ~80 MB and it contained Docker-related files (`Dockerfile`, `.dockerignore`, `docker-*.ts`, etc.) that are not part of the CRM itself.
- `_exclude_dirs.txt` — temporary file used during the copy process (not part of the deliverable).

### Why

The original project defaulted to Docker for database setup because it is the zero-configuration path. However, the project never required Docker — `DATABASE_URL` accepts any Postgres connection string and the migration/seed toolchain works with any reachable database. This copy removes the Docker assumption so the CRM can run against an existing local or hosted Postgres with no container runtime.

### Effect on user workflow

Instead of `docker compose up -d` to get a database, the user must:

1. Have a Postgres database already running, **or** start one using platform-native tooling.
2. Set `DATABASE_URL` in `.env` to point at that database.
3. Ensure the target database exists before running `bun run db:deploy`.

The rest of the workflow (`bun install`, `bun run db:deploy`, `bun run db:seed`, `bun run dev`) is unchanged.

## 4. Removed Build Artifacts and Cache Directories

### What changed

**Excluded directories (present in source, not copied):**

- `node_modules/` — installed dependencies. Will be recreated by `bun install` on the target machine.
- `.turbo/` — Turborepo build cache.
- `.eve/` — eve build output (agent build artifacts).
- `.output/` — agent output directory.
- `reports/` — reports directory (contents unknown; excluded to keep the copy clean).
- `.agents/` — agent-specific tooling directory at the repo root.

### Why

These are generated artifacts, caches or machine-specific directories. They are large, platform-dependent and should be regenerated by the build/install process on the target machine. Including them would bloat the repository and could introduce platform-specific state.

### Effect on user workflow

The user must run `bun install` after cloning to recreate `node_modules/`. The first `bun run dev` or `bun run build` will regenerate `.eve/` and `.output/` as needed.

## 9. PostgreSQL Authentication Note

### Background

The original `docker-compose.yml` used `POSTGRES_PASSWORD: postgres` and created a database named `crm` owned by the `postgres` user. The `.env.example` file references `DATABASE_URL= "postgresql://postgres:***@localhost:5432/crm?schema=public"`.

### What the operator must do

When using a local Postgres install (rather than the Docker container), the operator must ensure:

1. **The `postgres` role has a known password.** If the local install uses a different password, set it via `ALTER USER postgres PASSWORD 'newpassword';` or use the existing password in `DATABASE_URL`.

2. **The `crm` database exists.** Create it with `CREATE DATABASE crm;` if it does not exist.

3. **`DATABASE_URL` in `.env` reflects the actual credentials.** The connection string must match the local Postgres configuration.

These steps are documented in [INSTALL.md](./INSTALL.md) for each supported OS.

### Security note

The password `postgres` is a default and should be changed on any real deployment. The `.env.example` file uses `***` as a placeholder for the password, signaling that it must be set by the operator.
The INSTALL.md reinforces this: credentials belong in environment variables, never in documentation or code.

## 11. Verifying the Copy

To verify that the No-Docker copy is functional:

```sh
# From F:\crm_nodocker (or the cloned copy on the target machine)

# 1. Install dependencies
bun install

# 2. Configure .env (copy from .env.example and fill in real values)
cp .env.example .env
# Edit .env: set DATABASE_URL, BETTER_AUTH_SECRET, ALLOWED_SIGN_IN,
# and optionally GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET

# 3. Apply migrations
bun run db:deploy

# 4. (Optional) Seed demo data
bun run db:seed

# 5. Start the stack
bun run dev

# 6. Verify:
#    - App:  http://localhost:3000
#    - API:  http://localhost:3001
#    - Agent: http://127.0.0.1:2000
```

If all three services start and the database shows "connected" in the API logs, the copy is functional.
